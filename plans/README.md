  002 owns `getCommunityFirmwareRemoteData` / `getCommunityFirmware`; 003

## Scope decision, 2026-08-21 — this fork is the mainline, and it is ForkDrift-only

Two decisions were taken after the plans were first drafted. Both are recorded
here because they are not recoverable from the code.

**1. The fork is not abandoned; there is no upstream to return to.**
`crosspoint-reader/xteink-flasher` is **archived on GitHub** (`archived: true`,
last push 2026-05-20). Its final commit is `2b09cb4 "Add archived banner"`,
whose README text reads: _"This repo has been archived as
https://xteink.dve.al/ will start redirecting to https://crosspointreader.com/"_
— and that redirect is live. This fork is **5 ahead, 0 behind** `upstream/master`,
so it already contains everything upstream ever shipped, plus ~634 lines
upstream never had: Android WebUSB fallback, the PWA install flow
(`AndroidAlert.tsx`, `PWAInstallButton.tsx`, `flashEnvironment.ts`, +172 lines
in `EspController.ts`), and the GitHub Pages deploy. This repository is the only
living copy.

**2. The flasher installs ForkDrift firmware only.** Flashing stock vendor
(English/Chinese Xteink) firmware is out of the project's mission. Plan 003 was
therefore **rewritten**: it now _removes_ that path instead of hardening it.

The superseded draft — `003-verify-official-firmware-integrity.md`, which added
SHA-256 verification against the checksums the vendor API already publishes —
was deleted. Its design is recoverable from git history and is the right
approach **if this decision is ever reversed**. It was rejected only because the
feature is being dropped, not because the technique was wrong. Note in
particular the fact it uncovered: the vendor API returns
`data.checksums.{crc32,md5,sha1,sha256}` and `data.size`, all of which the
flasher currently discards.

Users who need stock vendor firmware keep a working route: download the `.bin`
themselves and use the existing **Write flash from file** upload, which plan 003
leaves fully intact.

## What these plans are built on (verified facts, 2026-08-21)

Recorded here so nobody has to re-derive them, and so a future reader can tell
when they have gone stale:

- `GET api.github.com/repos/Unintendedsideeffects/ForkDrift-crosspointReader/releases/latest`
  → **404**. Every ForkDrift release is created with `--prerelease` by
  `../crosspoint-reader/scripts/release.sh`, and `/releases/latest` excludes
  prereleases. The releases are addressed by channel tag instead
  (`/releases/tags/latest`).
- The ForkDrift `latest` release (name `3109-dev`) publishes
  `crosspoint-standard.bin`, `crosspoint-lean.bin`, `crosspoint-full.bin`,
  `crosspoint-lean-reset.bin`, `crosspoint-full-reset.bin`,
  `crosspoint-partitions.bin`, `firmware-20260726-39072d6.bin`. **None ends
  with `firmware.bin`**, which is what the current asset matcher looks for.
- The `nightly` release holds only `bootloader.bin` and `partitions.bin` — it
  is stale. No `stable` release exists yet.
- Upstream `daveallie/crosspoint-reader` answers **301** (repo renamed) and its
  latest release is `v1.5.0` with a plain `firmware.bin`. The current code works
  only because `fetch` follows redirects.
- The vendor's official-firmware API **already publishes checksums**
  (`crc32`, `md5`, `sha1`, `sha256`) and `size`, and the flasher discards all
  of them. Current official version is `V5.1.6`; the hardcoded fallback in
  `src/remote/firmwareFetcher.ts:26` claims `V3.1.1`.
- `https://gotaserver.xteink.com/...` does not answer; only `http://` does.

## Findings considered and rejected

So these are not re-audited next run:

- **Blanket `cleartextTrafficPermitted="true"` in the Android app**
  (`../ForkDriftApp/crosspoint-android/app/src/main/res/xml/network_security_config.xml:4`)
  — over-broad relative to its intent (the device is LAN-only), but Android's
  `domain-config` cannot express "any RFC1918 address" and the device IP is
  user-assigned, so no practical tightening exists. Not worth doing.
- **`ForkDriftApp` generally** — 20+ test classes including transport contract
  tests, no sensitive logging, nothing surfaced worth planning at `standard`
  depth. The `http://192.168.4.1` base URL (`WifiTransport.kt:397`) is the
  device's own AP address and is by design.
- **`isValidEsp32Image`'s unbounded `DataView`** (`src/utils/firmwareIdentifier.ts:53`)
  — constructs `new DataView(data.buffer, data.byteOffset)` without a length,
  which would over-read a subarray view. Every call site passes a fresh
  `.slice()`, so it is unreachable. Noted, not planned.
- **Adding a GitHub token to raise the API rate limit** — this is a static
  client-side app; any token shipped to the browser is public. Caching plus a
  readable error is the correct answer.

## Direction (options for the maintainer — not plans)

- **Make the flasher ForkDrift's actual install path.** `release.sh` already
  publishes a fixed five-asset set per channel with stable names, but the
  flasher exposes a single button. A lean/standard/full picker is nearly free
  given that naming contract already exists. Deliberately left out of plan 002
  so a UI change does not ride along with a correctness fix.
- **Unify the three install/update surfaces behind one published manifest.**
  There are three independent notions of "what firmware is available": the
  device's feature-store catalog (`docs/ota/feature-store-catalog.json`), the
  release channels (`release.sh`), and this flasher's hardcoded matcher. A
  single `channels.json` published alongside the release would let all three
  agree, and would make plan 002's bug unrepeatable by construction.
- **Decide which deploy target is canonical.** The repo deploys twice — GitHub
  Pages via `pages.yml` (static export, `next.config.ts:31-36`) and Vercel via
  `vercel.json`. Nothing currently _requires_ them to diverge once plan 003
  removes the plain-HTTP path, but maintaining two is a standing cost, and any
  future feature needing a server route (a proxy, an API) will force the
  question.
- **Rename the repository.** It is still called `xteink-flasher` and the
  package name in `package.json:2` is `"xteink-flasher"`, while the UI, the
  firmware it installs, and the project are all FORKDRIFT. Cosmetic, but the
  stale name is what made "should we just keep upstream?" a natural question in
  the first place.
